# 0016. Gloxi для програмування: VS Code, Zed, JetBrains та інші редактори

- Стан: Пропозиція (чернетка, чекає рішення Denys)
- Дата: 2026-11-04
- Пов'язано: [roadmap](../roadmap.md) розд. 2.3, 4, [ADR 0004](0004-local-model-engine.md), [ADR 0005](0005-gloxi-herkos-channel.md), [ADR 0008](0008-default-local-model.md), [ADR 0013](0013-herkos-rust.md), [`permissions.md`](../../herkos/docs/permissions.md) розд. 4, 8, 9.5, [Flatpak Gloxi](../../gloxi/flatpak/io.github.stdenis1980.Gloxi.yml)

## Контекст

Denys хоче, щоб Gloxi допомагав і з кодом: у VS Code / VSCodium, JetBrains, Zed, GNOME Builder, Neovim. Програмісти — перші, хто поставить Vilna і Gloxi, і перші, хто напише про них. Але допомога з кодом — це три різні речі з різними вимогами:

| Що | Приклад | Вимоги до моделі | Хто виконує дії |
| --- | --- | --- | --- |
| **Доповнення в рядку** (FIM) | сірий текст під курсором | маленька модель для коду, відповідь < 0,5 с | ніхто, лише підказка |
| **Чат про код** | «поясни помилку», «напиши тест для цієї функції» | загальна модель, 4–8B достатньо для простого | людина копіює або натискає «застосувати» |
| **Агент** | «виправ тест, запусти, повтори» | сильна модель з викликами інструментів, довгий контекст | агент сам читає, пише файли й запускає команди |

Що вже є і що обмежує вибір:

- **Модель:** локально Qwen3 4B Q4_K_M ([ADR 0008](0008-default-local-model.md)), від 16 ГБ RAM за швидкістю — Ministral 3 8B; хмара (Mistral Small) лише якщо людина її ввімкнула, через шлюз приватності. Для агента ні 4B, ні 8B локально не досить: вони плутаються в багатокрокових викликах інструментів (заміри `gloxi-bench`, 48–56 з 63 простих завдань).
- **llama-server** уже слухає `127.0.0.1:8080` з OpenAI-сумісним API ([`engine.py`](../../gloxi/src/gloxi/engine.py)), і Flatpak має `--share=network`. Тобто будь-яка програма на комп'ютері **вже зараз** може ним користуватися — але напряму, оминаючи маршрутизатор, шлюз приватності й журнал, і без жодного ключа. Це треба закрити незалежно від цього ADR (розд. «Рішення», п. 1).
- **Herkos** контролює лише дії, які проходять через нього (MCP-інструменти Gloxi). Якщо агент у редакторі (Cline, Continue agent, Copilot) сам запускає команди, Herkos про це не знає і не може знати. Чесно кажемо це людині.
- **Flatpak:** і Gloxi, і редактор можуть бути Flatpak. TCP на `127.0.0.1` працює між пісочницями; Unix-сокет — лише якщо обидві пісочниці бачать ту саму теку, а приватний сокет Herkos не має бути видно нікому. Запуск процесу з однієї пісочниці в іншій потребує `flatpak-spawn --host`, а це майже повний вихід з пісочниці.
- **Один розробник, Python.** Власне розширення для VS Code — TypeScript, окремий магазин (Open VSX і Marketplace), оновлення під кожну версію VS Code. Для JetBrains — Kotlin, ще один магазин.

## Варіанти

### А. Gloxi як локальний провайдер моделі (OpenAI-сумісний ендпоінт)

Gloxi віддає `http://127.0.0.1:<порт>/v1` (`/chat/completions`, `/completions` для FIM, `/models`). До нього вже вміють підключатися: Continue (VS Code / VSCodium, JetBrains), Cline і Roo Code, Zed (провайдер «OpenAI-compatible»), JetBrains AI Assistant (локальні моделі через OpenAI-сумісний сервер), Neovim (codecompanion, avante), Emacs (gptel). GNOME Builder власної інтеграції з моделями не має.

- **Важливо:** редакторам віддаємо не сам llama-server, а **проксі Gloxi** поверх маршрутизатора: локально за замовчуванням, хмара лише якщо людина її ввімкнула *і* дозволила цій програмі; шлюз приватності на шляху в хмару; ключ доступу для кожної програми; журнал «яка програма скільки запитів зробила».
- **Плюси:** найменше роботи (маршрутизатор і шлюз уже є); працює одразу в усіх редакторах; ніякого TypeScript.
- **Мінуси:** Herkos не бачить дій агента в редакторі; якість агента обмежена локальною моделлю; ми не керуємо інтерфейсом.

### Б. MCP-сервер «Gloxi» для чужих агентів

Gloxi віддає свої інструменти (файли, система, згодом календар) як MCP-сервер для VS Code, Zed, Claude Code тощо, з тими самими дозволами Herkos.

- **Плюси:** дії справді йдуть через Herkos.
- **Мінуси:** для коду майже нічого не дає — редактор і так має файли й термінал. Відкриває інструменти Herkos стороннім агентам, які ми не контролюємо (більша поверхня атаки prompt injection). Користь — для «ширших» завдань (календар, пошта), тобто не раніше альфи.

### В. Gloxi як агент через ACP (Agent Client Protocol)

ACP — відкритий протокол (Apache-2.0) між редактором і агентом поверх JSON-RPC у stdio, схожий на LSP. Його започаткував Zed; за станом на 2025 рік його підтримують Zed, JetBrains (спільно з Zed), Neovim (codecompanion, avante), Emacs; для VS Code — розширення спільноти (перевірити стан перед реалізацією). Редактор показує чат агента, дифи й термінал, а агент **просить** редактор прочитати чи записати файл (`fs/read_text_file`, `fs/write_text_file`), створити термінал (`terminal/create`) і **запитує дозвіл** (`session/request_permission`).

- **Плюси:** Gloxi лишається Gloxi: своя модель, свій маршрутизатор, свій шлюз, а кожен запит на файл чи команду Gloxi спершу пропускає через політику Herkos (рівень ризику, `tainted`, журнал), і лише тоді просить редактор. Один протокол на кілька редакторів, Python-бібліотека є, TypeScript не потрібен.
- **Мінуси:** потрібен цикл агента і модель, яка в ньому не губиться — локально це поки слабко, тож реальний агент іде в хмару за згодою. Більше роботи, ніж А.

### Г. Власне розширення для VS Code (і JetBrains)

- **Плюси:** повний контроль інтерфейсу, можна показувати діалог Herkos прямо в редакторі.
- **Мінуси:** TypeScript/Kotlin, два магазини, постійна гонитва за API редакторів — для однієї людини це окремий продукт. Continue і Cline уже роблять те саме добре й під відкритими ліцензіями.

## Рішення (пропозиція)

1. **Одразу, ще в 0.1 (окремий маленький PR):** llama-server запускається з випадковим ключем доступу на кожен запуск (`--api-key`, ключ лише в пам'яті Gloxi) або на Unix-сокеті всередині пісочниці, якщо наша версія llama-server це вміє (перевірити). Тоді модель не доступна іншим програмам і вебсторінкам в обхід Gloxi.
2. **Gloxi 0.2 (лютий — березень 2027): варіант А, «Gloxi для інших програм».**
   - Проксі Gloxi на `127.0.0.1` (порт за замовчуванням вибрати так, щоб не конфліктувати з Ollama 11434 і LM Studio 1234), вимкнений за замовчуванням. Людина вмикає його в налаштуваннях Gloxi і для кожної програми отримує окремий ключ («VS Code», «Zed»); ключ можна відкликати. Вмикання — дія R1 через Herkos-lite (новий запис у маніфесті), видно в журналі.
   - Запити йдуть через маршрутизатор: локально за замовчуванням; у хмару — лише якщо хмару ввімкнено і для цієї програми окремо дозволено («код цього проєкту може йти в хмару»).
   - **Режим шлюзу приватності «код»** на шляху в хмару: маскувати й блокувати секрети (ключі API, токени, паролі, приватні ключі, рядки з `.env`), адреси пошти й телефони в коментарях і даних; **не** маскувати імена змінних і функцій, бо це ламає код. Синтетичні тести: файл `.env`, приватний ключ SSH, токен GitHub у рядку коду.
   - Доповнення в рядку: **Qwen2.5-Coder 1.5B** як окреме необов'язкове завантаження (SHA-256, як для основної моделі), другий екземпляр llama-server, лише поки увімкнено проксі. На 8 ГБ — з попередженням про пам'ять; від 16 ГБ — пропонуємо.
   - Документація з готовими налаштуваннями для Continue (VSCodium / VS Code, JetBrains), Zed, Cline / Roo Code, Neovim (codecompanion), з чесною приміткою: «Дії, які агент у редакторі виконує сам, Herkos не контролює; обирайте в редакторі режим із підтвердженням».
   - Заміри: набір завдань коду в `gloxi-bench` (синтетичні, своїми словами: пояснити помилку, написати тест, знайти баг) і затримка FIM на ноутбуці. Мета — < 0,5 с на підказку.
3. **Етап 2 або альфа (не раніше літа 2027): варіант В, Gloxi як ACP-агент.** Команда `gloxi acp` — тонкий міст stdio ↔ запущений Gloxi (через той самий локальний ключ), щоб редактор у своїй пісочниці не запускав окрему модель і не потребував `flatpak-spawn --host`. Кожен запит агента до редактора спершу оцінює Herkos:

   | Що просить агент | Рівень |
   | --- | --- |
   | Читати файл у відкритому проєкті | R0 |
   | Читати файл поза проєктом, `.env`, ключі | заборонено |
   | Змінити файл у проєкті (через диф редактора, скасовується) | R1, дозвіл на сеанс |
   | Запустити тести чи збирання з білого списку проєкту | R2 |
   | Будь-яка інша команда в терміналі, встановлення пакетів, `git push` | R3, щоразу |
   | Вміст, який агент прочитав із файлів проєкту чи терміналу | зовнішній для Keros (`tainted`) |

   Агент локально — лише від 32 ГБ (Qwen3-Coder 30B-A3B або Devstral Small 2, заміри перед вибором), інакше хмара за згодою через шлюз у режимі «код».
4. **Варіант Б (MCP-сервер Gloxi для чужих агентів)** — не для коду; повертаємось до нього на альфі разом із календарем і поштою.
5. **Варіант Г (власне розширення)** — не робимо. Переглядаємо на беті, лише якщо у VS Code не буде робочої підтримки ACP, і тоді — найтонше розширення, яке лише запускає `gloxi acp`.
6. **GNOME Builder** вбудованої підтримки моделей не має; для нього — бічна панель Gloxi (схема 10.3 брифу) з інструментом «файли» в теці проєкту. Писати плагін для Builder не плануємо.

## Наслідки

- 0.2 отримує ще одну функцію; вона мала (маршрутизатор і шлюз уже є), але режим шлюзу «код» і FIM-модель — нова робота й нові заміри. Якщо 0.2 не встигає, першим переноситься FIM, потім режим «код» (тоді хмара для інших програм просто недоступна).
- Ми не обіцяємо безпеки Herkos для агентів у редакторі до варіанта В. В інтерфейсі й документації це сказано прямо.
- Нова модель для FIM — ще одна ліцензія в переліку й ще один файл на кілька сотень мегабайтів; в образ Vilna її не кладемо, лише завантаження за згодою.
- ACP — молодий протокол; якщо він не приживеться у VS Code, варіант В охопить Zed, JetBrains і Neovim, а для VS Code лишиться варіант А.

## Відкриті питання

1. Чи потрібен Gloxi для коду вже в 0.2, чи краще лишити 0.2 як є (календар, налаштування, монітор) і перенести варіант А на квітень 2027?
2. Чи дозволяти хмару для коду взагалі, чи лише локально, доки немає режиму шлюзу «код»?
3. Агент локально від 32 ГБ — чи варто це підтримувати, якщо таких машин у цільової аудиторії мало?
