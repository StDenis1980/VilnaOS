# 0005. Канал Gloxi ↔ Herkos: Unix-сокет із `SO_PEERCRED`

- Стан: Прийнято
- Дата: 2026-11-01
- Пов'язано: [roadmap](../roadmap.md) розд. 2.1 (Р6), [`herkos/docs/permissions.md`](../../herkos/docs/permissions.md) розд. 3 і 9

## Контекст

Кожна дія Gloxi має проходити через шлюз дозволів Herkos (принцип «один вхід»). У Vilna Gloxi і Herkos — окремі системні сервіси під різними користувачами; Herkos має точно знати, хто з ним говорить. У Gloxi 0.1 preview обидва працюють у сеансі одного користувача, але протокол має бути той самий, щоб на етапі 2 замінилася лише реалізація.

## Рішення

- **Транспорт:** Unix-сокет (`SOCK_STREAM`). Herkos перевіряє співрозмовника через `SO_PEERCRED` (uid, gid, pid) і відхиляє з'єднання від неочікуваного uid.
- **Формат повідомлень:** JSON-RPC 2.0, одне повідомлення на рядок (UTF-8, `\n` у кінці), так само як MCP через stdio. Методи й поля запиту дії — за permissions.md розд. 3; версія протоколу узгоджується першим викликом.
- **Gloxi 0.1 (сеанс користувача):** сокет `$XDG_RUNTIME_DIR/vilna/herkos.sock`, каталог з правами `0700`, сокет `0600`; Herkos-lite приймає лише власний uid.
- **Vilna (етап 2):** сокет у `/run/herkos/`, власник — системний користувач Herkos; дозволений uid — системний користувач Gloxi. Активація через systemd socket activation.

## Наслідки

- Не залежимо від D-Bus для критичного шляху безпеки; D-Bus лишається для інтеграцій з GNOME.
- У preview `SO_PEERCRED` лише захищає від інших користувачів системи, а не від процесів того самого користувача; це обмеження preview, і воно описане в документації.
- Протокол легко тестувати: тести шлюзу говорять з ним через ту саму пару сокетів, що й Gloxi, і стануть тестами відповідності для Rust-версії.
- Flatpak: сокет у `$XDG_RUNTIME_DIR` потрібно явно відкрити в маніфесті (`--filesystem=xdg-run/vilna`), якщо Herkos-lite працює поза пісочницею Gloxi. Остаточно вирішуємо під час пакування.

## Розглянуті варіанти

- **D-Bus.** Стандарт для GNOME, але складніша модель безпеки, більша поверхня атаки і залежність від брокера повідомлень на критичному шляху.
- **Локальний HTTP (localhost).** Не дає надійної ідентифікації процесу, відкритий для будь-якого локального процесу і браузера.
- **gRPC.** Важка залежність і генерація коду; переваги не потрібні для малого локального протоколу.
