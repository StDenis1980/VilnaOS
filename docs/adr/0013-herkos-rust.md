# 0013. Системний Herkos на Rust: один сервіс, план переходу

- Стан: Прийнято (Denys, 2026-11-02)
- Дата: 2026-11-02
- Пов'язано: [ADR 0003](0003-implementation-language.md), [ADR 0005](0005-gloxi-herkos-channel.md), [`herkos/docs/protocol.md`](../../herkos/docs/protocol.md), [`herkos/docs/permissions.md`](../../herkos/docs/permissions.md) розд. 9, [`herkos/rs/`](../../herkos/rs/)

## Контекст

ADR 0003 вирішив: Herkos-lite на Python для Gloxi 0.1, системний Herkos на етапі 2 — Rust. Стабільними тримаємо контракти (протокол, запит дії, маніфести), а Herkos-lite — їхня еталонна реалізація. Тепер треба вирішити, як саме переходити: скільки сервісів, хто показує вікно підтвердження, коли Rust замінює Python і на чому писати.

## Рішення

1. **Один сервіс `herkosd` на систему.** Він працює під системним користувачем `herkos` і розрізняє людей за uid з `SO_PEERCRED`: у кожного свої дозволи, журнал і сеанси. Сокет — `/run/herkos/` (ADR 0005). Ключі й журнал лежать там, куди процеси людини не дістають.
2. **Вікно підтвердження — окремий агент у сеансі людини** (`herkos-agent`). `herkosd` не має доступу до екрана людини. Він просить агента показати вікно і чекає відповіді. Спершу агент — наявне вікно GTK на Python (`herkos.dialog`); переписуємо його, лише коли буде причина.
3. **Rust замінює Herkos-lite скрізь, щойно вміє те саме** (крок 4 нижче: рішення, Mitos, інструменти, Keros). Тоді й на звичайному Linux Gloxi говорить з `herkosd` (у сеансі людини, як Herkos-lite зараз). Дві реалізації довше, ніж треба, не підтримуємо.
4. **Звичайні потоки std, без tokio.** З'єднань кілька, а не тисячі; асинхронний рантайм додав би коду в межу безпеки без користі. Залежності — мінімальні й поширені (`serde_json`, `rustix`), `unsafe` заборонено.

Кроки:

1. Тести відповідності протоколу ([`herkos/conformance/`](../../herkos/conformance/)): чорна скринька через сокет, проганяються проти обох реалізацій (`HERKOS_SERVE`).
2. Каркас: сокет, `SO_PEERCRED`, JSON-RPC, розбір запиту дії. Інструментів ще немає: кожна дія — `denied_unknown`.
3. Ядро рішень і журнал Mitos (той самий формат, ланцюжок хешів).
4. Клієнт MCP, інструменти «файли» й «копії», Keros (правила й модель).
5. Агент сеансу і тести відповідності з підтвердженнями.
6. Системний сервіс: користувач `herkos`, systemd socket activation, RPM.
7. Рівні R3–R4 і знімки btrfs. Рівні зроблено; знімки відкладено (рішення 3 листопада 2026): `/home` покривають копії інструмента «файли» (30 днів), а знімки кореня (snapper) прийдуть з інструментом оновлення системи. Знімки — [ADR 0026](0026-mitos-btrfs-snapshots.md) (10 листопада 2026).

## Наслідки

- Поки триває перехід, кожна зміна протоколу йде в обидві реалізації, а тести відповідності це перевіряють у CI.
- Один сервіс простіше оновлювати й перевіряти, але помилка в розділенні людей за uid зачепила б усіх. Тому ізоляція між uid — окремі тести на кроці 3.
- Вікно на Python лишається в сеансі людини, поза межею безпеки: воно лише показує запит і повертає відповідь, а рішення ухвалює `herkosd`.

## Розглянуті варіанти

- **Окремий `herkosd` для кожної людини.** Простіша ізоляція, але системні дії (оновлення, знімки btrfs) все одно потребують спільного сервісу, і тоді їх два.
- **Вікно підтвердження в самому `herkosd`.** Системному сервісу довелося б заходити в графічний сеанс людини; це ширші права і складніше на Wayland.
- **Тримати Herkos-lite для звичайного Linux назавжди.** Дві реалізації розходилися б, а Python-версія не отримала б тих самих перевірок.
- **tokio.** Зручно для мережевих сервісів із тисячами з'єднань; тут лише додає залежностей.
