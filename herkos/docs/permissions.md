# Модель дозволів Herkos

Стан: **чернетка v0.1** (листопад 2026). Документ описує, як Herkos вирішує, чи може асистент Gloxi виконати дію, коли питає користувача і як дію можна скасувати. Це специфікація, а не опис готового коду: кожен розділ може змінитися після першого прототипу.

## 1. Принципи

1. **Один вхід («Монемвасія»).** Gloxi не має прямого доступу до системи, файлів чи мережі. Кожна дія стає запитом до шлюзу дозволів Herkos, і лише він її виконує або відхиляє. Обхідних шляхів немає: якщо дія не пройшла через шлюз, вона не відбулася.
2. **«Прив'язаний до щогли».** Gloxi чує все, що користувач дозволив йому бачити, але діє лише з дозволу. Читати можна широко, змінювати — обережно, діяти назовні від імені людини — лише з підтвердженням.
3. **Найменші привілеї.** Сервіс Gloxi працює під окремим системним користувачем без прав адміністратора. Права, яких бракує, Herkos отримує на одну дію, а не назавжди.
4. **Модель не є суб'єктом довіри.** Рішення шлюзу не залежить від того, що «каже» модель. Модель лише пропонує дію; рівень ризику визначає Herkos за власними правилами.
5. **Усе, що прийшло ззовні, — дані, а не інструкції.** Вміст вебсторінок, листів, файлів і відповідей інструментів ніколи не може підвищити права (див. [Keros](#6-keros--фільтр-prompt-injection)).
6. **Видимість і відкат.** Кожна дія записується в журнал Mitos. Де це технічно можливо, перед зміною робиться знімок, і дію можна скасувати.
7. **Приватність за замовчуванням.** Дані, що йдуть у хмарну модель, спершу проходять шлюз приватності на пристрої.
8. **Відмова за замовчуванням.** Невідома дія, невідомий інструмент або помилка в оцінці ризику означають «заборонено», а не «дозволено».

## 2. Терміни

| Термін | Значення |
| --- | --- |
| **Дія** | Одна операція, яку пропонує Gloxi: прочитати файл, створити подію в календарі, надіслати лист, встановити пакет |
| **Запит дії** | Структурований опис дії, який Gloxi передає шлюзу (розд. 3) |
| **Інструмент** | MCP-сервер або системний інтерфейс (D-Bus, portal), через який дія виконується |
| **Маніфест інструмента** | Файл Herkos, що для кожного інструмента й операції задає рівень ризику, ресурси й можливість відкату |
| **Дозвіл** | Рішення користувача, що дозволяє дію або клас дій у певних межах і на певний час |
| **Забруднення (taint)** | Позначка, що в контексті моделі є вміст із ненадійного джерела |

## 3. Потік дії

```
 Користувач ──► Gloxi (модель планує дію)
                   │
                   ▼  запит дії
          ┌──────────────────────────── Herkos ────────────────────────────┐
          │ 1. Перевірка формату і маніфесту  (невідоме → відмова)         │
          │ 2. Keros: позначки забруднення, перевірка на prompt injection  │
          │ 3. Оцінка рівня ризику R0–R4                                   │
          │ 4. Пошук чинного дозволу / запит підтвердження в користувача   │
          │ 5. Mitos: запис у журнал, знімок перед зміною                  │
          │ 6. Виконання через інструмент (MCP / D-Bus / portal / polkit)  │
          │ 7. Mitos: запис результату; відповідь проходить Keros назад    │
          └────────────────────────────────────────────────────────────────┘
                   │
                   ▼
            Результат для Gloxi
```

Запит дії містить щонайменше:

```yaml
action_id: 01J...            # унікальний ідентифікатор для журналу
tool: org.vilna.mcp.files    # інструмент
operation: write             # операція з маніфесту
resources:                   # на що впливає дія
  - file:///home/<user>/Documents/zvit.odt
reason: "Користувач попросив виправити дату у звіті"   # пояснення для людини
origin:
  user_turn: 42              # з якої репліки користувача почалася дія
  tainted: true              # у контексті є ненадійний вміст (ставить Herkos, не модель)
  sources: [email:<id>]
```

Поле `tainted` і рівень ризику виставляє Herkos, а не модель. Значення, які прислала модель, ігноруються.

## 4. Рівні ризику

Рівень визначає маніфест інструмента для пари «інструмент + операція», а потім коригують модифікатори (розд. 4.2).

| Рівень | Назва | Приклади | За замовчуванням |
| --- | --- | --- | --- |
| **R0** | Нейтральні | Котра година, стан батареї, список відкритих вікон, пошук у вже проіндексованих метаданих | Виконується без питань, пишеться в журнал |
| **R1** | Читання особистого | Прочитати файл у дозволеній папці, переглянути календар, прочитати листи | Дозвіл на клас дій, даний один раз (наприклад, «Gloxi може читати календар») |
| **R2** | Зворотні зміни | Створити або змінити файл, подію в календарі, чернетку листа; змінити налаштування теми, звуку | Дозвіл на клас дій; відкат через Mitos. Перший раз — підтвердження |
| **R3** | Важкозворотні або системні | Видалити файли, встановити чи видалити програму, змінити мережу, оновити систему, змінити дозволи інших програм | Підтвердження **щоразу** (або в межах короткого сеансу, див. 5.3) |
| **R4** | Незворотні або від імені людини назовні | Надіслати лист чи повідомлення, оплатити, опублікувати, передати файл іншій людині, видалити без знімка, змінити пароль чи ключі | Підтвердження **щоразу**, з показом точного вмісту. Постійний дозвіл неможливий |

Окремо стоїть **заборонене**: дії, які Herkos не виконує взагалі, навіть із підтвердженням. Наприклад: вимкнути або змінити сам Herkos, змінити журнал Mitos, прочитати збережені паролі в чистому вигляді, вимкнути знімки.

### 4.1. Як визначається рівень

1. Базовий рівень береться з маніфесту Herkos для інструмента й операції.
2. Анотації MCP-сервера (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) — лише підказки від самого інструмента, тому їм не довіряємо. Herkos бере **вищий** із двох рівнів: з маніфесту і з анотацій. Анотації можуть рівень лише підвищити.
3. Інструмент без маніфесту отримує R3 для читання і R4 для решти, доки маніфест не з'явиться.

### 4.2. Модифікатори

| Умова | Ефект |
| --- | --- |
| У контексті є забруднений вміст (`tainted`) і дія — R2 або вище | +1 рівень; R4 показує, з якого джерела прийшла вказівка |
| Дія стосується ресурсу поза дозволеними межами (інша папка, інший обліковий запис) | +1 рівень |
| Масова дія (понад N ресурсів за раз, N задається в налаштуваннях) | +1 рівень |
| Дія не має відкату (Mitos не може зробити знімок) | Щонайменше R3 |
| Дані виходять за межі пристрою (мережа, хмара, інша людина) | Щонайменше R3; з особливими категоріями даних — R4 |

Рівень ніколи не знижується модифікаторами: їх можна лише додавати.

## 5. Підтвердження

### 5.1. Коли потрібне підтвердження

- R0 — ніколи.
- R1 — один раз на клас дій (стає постійним дозволом, який видно й можна відкликати в налаштуваннях).
- R2 — перший раз для класу дій, далі за постійним дозволом. Кожну дію можна скасувати.
- R3 — щоразу, або в межах сеансу (5.3).
- R4 — щоразу, без винятків.
- Будь-яка дія, яку шлюз приватності позначив як «особливі категорії даних», — щоразу.

### 5.2. Як виглядає підтвердження

Діалог показує сам Herkos (окремий процес), а не Gloxi, щоб модель не могла підробити або змінити його текст. Діалог містить:

- що саме буде зроблено, простими словами, і точний вміст для R4 (текст листа, отримувачі, сума);
- на які ресурси вплине дія;
- чи можна її скасувати;
- якщо дію запропоновано через забруднений вміст — звідки він прийшов («Вказівка з листа від …»);
- кнопки «Дозволити один раз», «Дозволити на цей сеанс» (лише R2–R3), «Відхилити».

Кнопку «Дозволити» не можна натиснути програмно: діалог приймає лише реальне введення користувача (не через AT-SPI і не від самого Gloxi). Таймаут без відповіді означає відмову.

Голосові підтвердження для R3–R4 вимагають додаткової дії на екрані або фрази, яку модель не може передбачити, щоб синтезований голос або аудіо з відео не могли дати дозвіл.

### 5.3. Межі дозволів

Кожен дозвіл має:

- **клас дій** (інструмент + операція);
- **межі ресурсів** (наприклад, лише `~/Documents`, лише календар «Робота»);
- **тривалість**: один раз, сеанс (до блокування екрана або 30 хв бездіяльності), постійно (лише R1–R2).

Усі постійні дозволи видно в налаштуваннях Vilna, кожен можна відкликати одним натисканням.

## 6. Keros — фільтр prompt injection

Keros стоїть на шляху **всіх** даних, які повертаються до моделі: результати інструментів, вміст файлів, листів, сторінок, тексти з інших програм через AT-SPI.

Завдання:

1. **Позначати походження.** Кожен фрагмент контексту отримує мітку джерела: користувач, система Vilna, інструмент, зовнішній вміст. Зовнішній вміст ставить на сесію позначку `tainted`.
2. **Розділяти дані й інструкції.** Зовнішній вміст передається моделі в явно позначених межах як дані. Інструкції з цих меж не мають сили, навіть якщо модель їх виконає: рівень ризику все одно підвищується (4.2).
3. **Виявляти спроби.** Правила і локальний класифікатор шукають типові ознаки injection (вказівки «ігноруй попередні інструкції», приховані символи, текст білим на білому, підозрілі URL у даних). Знахідка не блокує читання, але підвищує ризик подальших дій і показується користувачу.
4. **Перевіряти зворотний напрям.** Аргументи запиту дії перевіряються на ознаки витоку: дані, що з'явилися з забрудненого джерела, не можуть потрапити в URL, отримувачів листа або команду без R4-підтвердження.

Keros не вважається достатнім захистом сам по собі: класифікатор може помилятися. Остаточний бар'єр — рівні ризику й підтвердження, які не залежать від того, чи помітив Keros атаку.

## 7. Mitos — журнал і відкат

### 7.1. Журнал

- Кожен запит дії, рішення шлюзу, підтвердження користувача і результат записуються в журнал, лише для додавання (append-only).
- Записи пов'язані ланцюжком хешів, щоб непомітно змінити або видалити запис було неможливо.
- Журнал зберігається локально, доступний для запису лише Herkos, для читання — користувачу. Gloxi може читати лише підсумки власних дій.
- Журнал не містить чутливого вмісту в чистому вигляді: для листів і файлів пишеться опис і хеш, а не вміст.
- Користувач бачить журнал у зрозумілому вигляді: «Сьогодні о 14:02 Gloxi змінив файл zvit.odt, бо ви попросили виправити дату. [Скасувати]».

### 7.2. Відкат

| Що змінюється | Як Mitos робить відкат |
| --- | --- |
| Системні файли, пакети, налаштування в `/etc` | На Aeon / Kalpa корінь незмінний, а зміни проходять через `transactional-update`, який сам створює знімок btrfs (snapper). Mitos прив'язує знімок до запису в журналі; відкат означає повернення до знімка з перезавантаженням |
| Файли користувача в `/home` | Підтом `/home` не входить до знімків кореня. Mitos робить легкий знімок btrfs потрібного підтому (або копію змінюваних файлів) перед дією R2–R3 і зберігає його обмежений час |
| Налаштування робочого середовища (dconf / KConfig) | Зберігається попереднє значення ключа |
| Календар, контакти (CalDAV / CardDAV) | Зберігається попередня версія об'єкта; відкат — зворотна операція на сервері, якщо сервер її дозволяє |
| Листи, повідомлення, оплати, публікації | **Відкат неможливий.** Саме тому такі дії мають R4 |

Політика зберігання знімків (скільки й як довго) — відкрите питання (розд. 11), бо вона впливає на дисковий простір на мінімальному залізі. Відправна точка — 30 днів, як історія версій в OneDrive (так уже працює інструмент «файли» в Herkos-lite).

## 8. Шлюз приватності

Шлюз приватності — частина Herkos, увімкнений за замовчуванням. Він стоїть між маршрутизатором моделей і хмарою: усе, що йде в хмарну модель, спершу обробляється на пристрої.

1. **Виявлення.** Локальні правила і мала модель знаходять персональні дані: імена, адреси, телефони, email, номери документів, IBAN, номери карток, координати.
2. **Псевдонімізація.** Знайдені дані замінюються стабільними замінниками в межах розмови (`[ОСОБА_1]`, `[IBAN_1]`). Таблиця відповідності зберігається лише на пристрої і ніколи не передається. Відповідь хмари проходить зворотну заміну локально.
3. **Особливі категорії** (ст. 9 GDPR: здоров'я, релігія, політичні погляди, сексуальне життя, біометрія, етнічне походження тощо), а також дані дітей **блокуються** до явного підтвердження користувача. Без підтвердження запит обробляється лише локально або не обробляється.
4. **Маршрутизація.** Якщо запит можна обробити локальною моделлю, шлюз віддає перевагу їй. Користувач може заборонити хмару повністю.
5. **Журнал.** Mitos фіксує, що і в якому обсязі пішло в хмару (без самого вмісту).

Формулювання для користувачів і маркетингу: «чутливі дані маскуються на пристрої». Не «анонімно»: псевдонімізовані дані за GDPR залишаються персональними, а контекст може дозволити повторну ідентифікацію.

Шлюз переноситься з власних напрацювань засновника і має стати спільним компонентом, який можна використовувати й поза Vilna (тому під Apache-2.0, див. [`LICENSING.md`](../../LICENSING.md)).

## 9. Зв'язок із системними механізмами

### 9.1. Ізоляція процесів

- Сервіс Gloxi — окремий системний користувач, юніт systemd з жорсткими обмеженнями (`ProtectSystem=strict`, `ProtectHome=yes`, `NoNewPrivileges=yes`, обмежений набір syscall, мережа лише до Herkos і маршрутизатора моделей).
- Herkos — окремий сервіс; лише він має доступ до системних інтерфейсів від імені користувача. Gloxi спілкується з Herkos через приватну шину D-Bus або Unix-сокет.
- MCP-сервери інструментів запускає Herkos, кожен у власній пісочниці з доступом лише до потрібних ресурсів.

### 9.2. polkit

- Herkos оголошує власні дії polkit (`org.vilna.herkos.*`) для системних операцій рівня R3–R4.
- Для системних змін Herkos не обходить polkit, а викликає звичайні системні сервіси (PackageKit, NetworkManager, systemd), які самі запитують polkit. Автентифікацію адміністратора виконує стандартний агент polkit робочого середовища: Herkos не бачить і не зберігає пароль.
- Правила polkit Vilna (`/etc/polkit-1/rules.d/`) забороняють користувачу Gloxi будь-які дії напряму, тож навіть скомпрометований Gloxi не може звернутися до системних сервісів в обхід Herkos.
- Якщо дія потребує і підтвердження Herkos, і автентифікації polkit, користувач бачить спершу діалог Herkos (що і навіщо), потім діалог polkit (хто ви). Об'єднати їх в один діалог — відкрите питання.

### 9.3. Flatpak portals

- Програми у Vilna ставляться переважно як Flatpak. Для дій із ними Herkos використовує xdg-desktop-portal: вибір файлів, знімки екрана, запуск програм, сповіщення, фонова робота.
- Якщо portal сам показує діалог дозволу (наприклад, знімок екрана), Herkos не дублює його, а записує рішення portal у журнал. Рівень ризику при цьому не знижується.
- Herkos читає й змінює дозволи інших Flatpak-програм через сховище дозволів portal лише як дію R3.

### 9.4. D-Bus і AT-SPI

- Керування програмами йде через D-Bus API програм і робочого середовища (KDE / GNOME), а де їх немає — через AT-SPI (доступність).
- Для кожного D-Bus-інтерфейсу, який використовує Herkos, є маніфест із рівнем ризику для кожного методу. Невідомі методи — заборонено.
- AT-SPI дає змогу «натискати кнопки» в будь-якій програмі, тому дії через нього за замовчуванням мають щонайменше R2, а натискання в діалогах безпеки (polkit, Herkos, менеджер паролів) заборонене.
- Текст, прочитаний через AT-SPI з інших програм, вважається зовнішнім вмістом для Keros.

### 9.5. MCP-інструменти

- Інструменти Gloxi — MCP-сервери: файли, програми, налаштування, календар (CalDAV), пошта (IMAP / SMTP).
- Gloxi бачить список інструментів, але виклики йдуть лише через Herkos, який виступає посередником між MCP-клієнтом Gloxi і MCP-серверами.
- Кожен сервер має маніфест Herkos: операції, рівні ризику, межі ресурсів, можливість відкату. Сторонній MCP-сервер без маніфесту працює з найсуворішими рівнями (4.1).
- Відповіді MCP-серверів — зовнішній вміст для Keros.

## 10. Модель загроз (стисло)

| Загроза | Захист |
| --- | --- |
| Prompt injection у листі, файлі, сторінці | Keros, позначка `tainted`, підвищення ризику, підтвердження R3–R4 |
| Модель «вирішила» зробити шкідливу дію сама | Рівень ризику не залежить від моделі; підтвердження показує Herkos |
| Скомпрометований процес Gloxi | Ізоляція systemd, правила polkit, Gloxi не має прямого доступу до системи |
| Шкідливий або помилковий MCP-сервер | Пісочниця, маніфест Herkos, анотації лише підвищують ризик |
| Підроблене підтвердження (через AT-SPI, синтезований голос) | Діалог приймає лише реальне введення; голос для R3–R4 потребує додаткового кроку |
| Витік персональних даних у хмару | Шлюз приватності, особливі категорії блокуються |
| Приховування слідів | Журнал Mitos лише для додавання, з ланцюжком хешів |

Поза межами цієї моделі: фізичний доступ до розблокованого пристрою, скомпрометоване ядро або прошивка, зловмисний адміністратор системи.

## 11. Відкриті питання

- Точні межі сеансу для дозволів R3 (час, блокування екрана, зміна мережі).
- Політика зберігання знімків Mitos для `/home` на дисках малого розміру. Для інструмента «файли» в Herkos-lite ухвалено 30 днів, як в OneDrive; для знімків btrfs у Vilna — ще ні.
- Чи об'єднувати діалоги Herkos і polkit в один.
- Хто підписує маніфести сторонніх MCP-серверів (формат маніфесту v0.1 — у [`protocol.md`](protocol.md), розд. 5).
